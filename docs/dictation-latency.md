2026-11-07：用户反馈部分微信听写直到说完才出现文字。本机系统日志在
12:02:08 开始收音、12:02:21 停止收音后，12:02:25 才记录旧连接关闭并重建。
这与旧连接等待响应后恢复相符，但缺少首个识别文字的阶段日志，不能据此
证明每次延迟均来自同一原因。

本轮先处理用户指定的 1、2、4 项，3（串行上传积压）及 5（仅润色字段的
预览）由两个 GLM 5.3 flash 会话独立验证，再决定是否调整。

## 修改前验收约定

- 闲置超过 60 秒的微信连接在预热/使用前重建；预热检查本身不能刷新闲置
  时钟，成功语音回复才刷新。近期成功连接仍可复用。
- 复用连接的首包使用 3 秒恢复窗口；首包失败仅重连一次，逐字节重发同一
  音频包、序号、累计字节数及语音标识。新连接、后续包与定稿等待保持 15 秒。
- Esc 及任务取消必须结束正在等待的 Foundation WebSocket 读取，取消不
  得启动重连；等待独占预热的租约也必须向该预热传递取消。
- 重复临时稿不重复更新 UI；Unicode 编码不同的文字仍须交付显示。定稿、
  空定稿、修订、继续录音、段落顺序、发送和一次性输入规则不变。
- 浮窗布局不在正在布局的路径中再次强制遍历子树；保留小点开合、文字
  过渡、动态高度与波形/thinking 转换。

## 回归依据

先添加受控连接、精确最终文本与重发音频断言，以及真实本机 WebSocket
取消/超时/连续收包回归，再修改运行行为。检查最近连接复用、过期连接
重建、预热不延寿、首包失败完整重发、取消不重连、重复稿去重与 Unicode
编码修订；发布前运行 `./Scripts/test.sh` 并核对实际原生浮窗。

## 第 5 项验证与实施决定

两个验证会话均通过 super.engineering 启动，模型明确指定为
`zhipu/glm-5.3-flash`，团队 `d811add6b8cd`。预览验证报告保存在
`/tmp/openvoice-glm-preview-verification.md`；其上游对照与合成回复实验
证明了本地的仅润色稿缺预览路径，但没有证明本次真实服务端实际返回过
该序列，亦没有供应商 schema/在线录音证据。

父 Agent 在真实 `WeTypeEngine` 上先增加回归：输入音频流仍未结束时仅
返回润色字段，应立即出现预览；结束后必须精确返回完整润色稿。该用例
修改前失败。实施范围进一步收窄为：当前回复没有原稿、此前也没有收到
原稿，且本次润色字段非空时，使用该润色文字作为预览。已有原稿的预览
路径、两个字段不拼接、最终结果二选一及轮询规则保持原样。

仅润色预览与已有原稿的两个用例均通过。没有采纳报告中直接使用旧
`polished` 变量的示例片段；实际回退使用当前 `reply.polished`，并由生产
引擎的精确预览及最终稿断言验证。

## 浮窗几何与日志

真实原生预览仍出现无穷坐标时，使用 LLDB 在 `_os_log_fault_impl`
断点定位到 `DictationHUDSurface.layout` 的提示文字矩形：8 点开合窗口
小于内边距，`insetBy` 生成 null rect。改为非负宽高的显式矩形；既有
点状进出场、文字及 thinking 回归继续验证可见内容。

相同稿件直接去重；编码不同的 Unicode 修订继续交付。设置通知异步
合并，只有浮窗大小或减少动态效果状态改变时才重新配置，避免在
SwiftUI 更新中同步进入原生布局。静音回归的重复消息排空改用 main queue
FIFO 屏障，继续断言重复文字不会延长语音活动。

新增系统日志分类 `do.j3.openvoice / WeTypeTiming`，记录 prepare、start、
first-reply、first-raw、first-polished、reconnect、finished/ended 的耗时、
逻辑请求数量和最长请求耗时。日志只含随机关联标识及阶段数值，不记录
识别文本、音频内容、密钥或设备凭据。预热时长与 run 时长分别记录。

## 第 3 项验证与实施决定

上传验证报告保存在 `/tmp/openvoice-glm-upload-verification.md`，两个角色
均已上报 done。父 Agent 核对生产循环后采纳其静态结论：每批最多 120ms
音频、串行等待一次回复，回包持续慢于该周期时会积压；服务端是否接受
更大批次、并发或流水线仍无实测依据。

报告的具体延迟数值不作为发布依据：事件模型中前导静音/真实音频的
时间表与生产节流不同，还加入了未经验证的单帧补入规则；本地探针只
打印了第一批发送时的计数，不能证明 AsyncStream 存在单帧缓冲限制。
生产 for-await 在积满 6 帧后清空数组，结束后的 `while packets.count > 6`
在当前循环中不可达，因此也不据此改写所谓结束残帧拆分。

决定保留当前分包大小、请求串行顺序、序号与最终润色轮询；本轮仅加
阶段/请求耗时诊断。没有把模拟当作本次真实卡顿的根因证明。
